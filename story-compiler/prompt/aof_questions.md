## Q3. 視点（POV）モジュール（章6）の設計

メモの内容を整理すると、3つの軸がある：

1. **カメラ設置場所** — 誰の上にカメラがあるか（POV character）
2. **カメラ解像度** — その主体の認知能力レベルで描写するか、代弁的（三人称で洞察力を上げる）か
3. **視点ポリシー一貫性** — 最初に宣言した視点ルールからの逸脱をerrorにする

```yaml
# 視点モジュール案
pov_policy:
  declaration_required: true  # 物語開始前に宣言必須
  fields:
    pov_type: [first_person, third_person_limited, third_person_omniscient, etc.]
    camera_subject: "誰の上にカメラがあるか"
    resolution_mode:
      - subject_native     # 主体の認知レベルそのまま
      - elevated_narrator  # 三人称で主体より高い洞察を付与
    per_scene_override: true  # シーンごとにカメラ変更可能か

  consistency_check:
    violation: compile_error  # ポリシー違反はエラー
    note: "未熟な主体のカメラなら、その主体が想像しうることしか繊細に描けない"
```

## Q4. 描写 vs 語り（Show vs Tell）アルゴリズム（章26）

メモに書かれたロジックを整理するとこうなる：

```
前提: 本題（このシーンで描きたいこと）が未定義 → compile_error

判定フロー:
1. 面白さスコア（McKee基準で算出） < 閾値 → 語り（要約）を選択
2. 面白さスコア高い && 本題から逸れている → 語り（要約）を選択
3. 人物が多い → 語りを推奨（情報過多防止）
4. それ以外 → 描写を試みよ
5. 語り（要約）が連続 → warning（高等テクニックであり明確な理由が必要）
```

**質問：「面白さスコア」はどう算出する？** 候補：
- (a) value_change（価値変化）の有無・大きさで測る（McKee的にはこれが自然）
- (b) 読者の好奇心レベル × 価値変化の掛け算
- (c) 別の基準？

**回答：**
aでいい気がします。

## Q5. ティーンエイジスカース（章4）の使い所

メモに「使い所が整理されていない」とある。デイヴィッド・ロッジが言う典型的な使い所は：

- **語り手が未熟（子供・ティーン・教育水準の低い人物）なのに、その語りを通して読者がメタ的叡智を受け取る**構造
- 効果：皮肉（irony）、哀切さ（pathos）、読者の優越的共感

Constrainでの使い所候補：
- 幼少期シーン（childhood.md）で幼い語り手を使い、読者だけが先の展開の残酷さを知っている構造
- 未熟なキャラクターの一人称パートがある場合

→ これをコンパイラに組み込むなら、**視点モジュール（Q3）の `resolution_mode: subject_native` かつ語り手が未熟なとき、自動的に「ティーンエイジスカース適用可能」とinfoを出す**設計が自然だが、それでいいか？

## Q7. 理解不足の章への補足

### 12. 場の感覚（Sense of Place）
ロッジが言う「場の感覚」とは：**物語の舞台（場所）が単なる背景ではなく、登場人物の心理・テーマ・物語の意味と有機的に結びついている状態**のこと。
- 天気（章18）もこの一部。場所の描写が感情や主題を映し出す鏡になっている
- 悪い例：場所の描写がただの設定説明（「東京の渋谷で…」）
- 良い例：場所の質感が人物の内面状態を増幅・対比している

→ これを天気（章18）と合わせて `17_symbolism-and-image.yaml` の拡張にするか、独立モジュール `26_setting-as-mirror.yaml`（場の感覚 + 天気の象徴）にするか？

**回答：**
ここに関しては、draw.io等で解説してほしい。アルゴリズムをともに設計したい。

### 32. エピファニー（Epiphany）
ジェイムズ・ジョイスが提唱した概念。**日常的な瞬間の中に、突然意味が結晶化する一瞬**のこと。
- 劇的な出来事ではなく、何気ない言葉・光景・動作が引き金になって、人物（または読者）が深い真実をハッと悟る
- McKeeの「価値変化」の特殊形：外的に大きなことが起きなくても、内的に決定的な変化が起きる
- 純文学では特に重要な技法

→ コンパイラ的には、`19_scene-mastery.yaml` の「シーンの価値変化」チェックで、**外的イベントが小さいのに価値変化が大きいパターン**をエピファニーとして検出・許容する設計が考えられるが、どうか？
