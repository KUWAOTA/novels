# 創作 Discord サーバー設計案

元の構想: [構想.txt](構想.txt)  
作成日: 2026-09-24

## 前提と目的

既存の空サーバーを使い、招待制の小規模な創作コミュニティから始める想定。作品を持ち込む参加者が、自作の相談、設定の拡張、ファンアート、二次創作を行い、作業通話もできるようにする。作品ごとの公開範囲と二次創作の許諾は作品主が決める。Discord 上の提案は、作品主が明示して採用するまで公式設定にしない。

## 1. サーバーを編集するために必要な情報

既存サーバーを編集する場合、次を共有してもらう。

1. **サーバーの招待リンクまたはサーバー ID**。招待リンクは招待期限と利用回数を絞り、公開ファイルには記録しない。
2. **操作経路**。ユーザーがログイン済みの Discord を操作できる接続手段、またはユーザー自身が設定するための画面共有。サーバー ID だけでは編集できない。
3. **権限**。チャンネル・ロール・AutoMod を設定できる権限が必要。コミュニティ設定や Bot 連携には追加の管理権限が必要な場合がある。安全のため所有者アカウントやパスワード、Discord ユーザートークンは渡さない。Bot を開発する場合も秘密鍵や Bot トークンをチャットやリポジトリに貼らない。
4. **設計上の決定**。サーバー名、公開か招待制か、最初に扱う作品と作品主、作品ごとの閲覧範囲、批評と二次創作の許諾、管理担当者。

サーバーを新規作成する場合も、ユーザーの Discord アカウントで作るのが自然。所有権をユーザーが持てるため、既存の空サーバーを利用することを推奨する。**この設計段階では実サーバーを変更しない。**

## 2. 初期構成

| カテゴリ | チャンネル | 種類と用途 |
|---|---|---|
| はじめに | `#はじめに` | 閲覧専用。サーバーの目的、導線、投稿例 |
| はじめに | `#ルールと権利` | 閲覧専用。批評、二次創作、ネタバレ、引用・転載のルール |
| はじめに | `#お知らせ` | 運営投稿のみ |
| 交流 | `#自己紹介` | 創作ジャンル、作品紹介、求める交流を記入 |
| 交流 | `#雑談` | 作品をまたぐ会話 |
| 交流 | `#作品チャンネル申請` | 新しい作品の登録依頼。テンプレートを固定 |
| 交流 | `#創作相談` | 作品チャンネルがまだない人の相談 |
| 作品群 | `#作品名` | **作品ごとにフォーラムチャンネルを1つ**。作品主と概要をチャンネル説明に明記 |
| 作業通話 | `🔊 作業室` | 作業イプ、画面共有。最初は1室 |
| 作業通話 | `🔊 相談室` | 声で相談したい場合の予備室。必要になってから追加可 |
| 運営 | `#通報・運営メモ` | 運営だけ閲覧。AutoMod の通知先にも使う |
| リポジトリ | `#公開更新` | 必要になったときのみ。承認済みの更新情報を投稿 |

作品フォーラム内では、**投稿1件を1つの話題**にする。例: `【キャラ】主人公の動機`, `【シーン】第3章の対立`, `【設定】舞台の交通`, `【相談】結末の選択肢`, `【ファンアート】人物画`, `【二次創作】短編`。タグは `人物` `シーン` `世界・設定` `相談中` `アイデア` `ファンアート` `二次創作` `ネタバレ` `採用済み` を候補とする。作品主が採用した案だけ `採用済み` と記し、出典の投稿リンクを残す。フォーラム投稿は非アクティブ時に古い投稿へ移るため、重要な決定は冒頭の索引投稿かリポジトリ側にも要約する。

フォーラムチャンネルを使うにはサーバーの **コミュニティ機能**を有効化する必要がある。Discord 公式の説明では、フォーラムは話題ごとの継続的な議論に適し、通常のテキストチャンネルから作るスレッドより探しやすい。[Discord: Forum Channels FAQ](https://support.discord.com/hc/en-us/articles/6208479917079-Forum-Channels-FAQ)

### 作品チャンネルの増設

参加者は `#作品チャンネル申請` に次を投稿する: 作品名、作品主、短い紹介、ネタバレ範囲、批評の受け入れ方、ファンアート・二次創作の許諾、リポジトリとの連携希望。運営が既存の作品と重複しないか、権利と公開範囲を確認してフォーラムを作る。頻繁に増えるようになったら申請フォームや Bot に移す。一般参加者へサーバー全体の「チャンネル管理」権限を渡して自動増設する設計にはしない。

作品数が増えたらカテゴリをジャンルや五十音で分け、参加者が見たい作品を選べる導線を用意する。Community Onboarding はその段階で検討する。設定要件があるため、少人数の招待制では初日から無理に有効化しない。[Discord: Community Onboarding FAQ](https://support.discord.com/hc/en-us/articles/11074987197975-Community-Onboarding-FAQ)

## 3. 権限と運営

| ロール | 主な権限 |
|---|---|
| 管理者 | サーバー設定、ロール、チャンネル、Bot を管理。最少人数 |
| モデレーター | 投稿・通話の管理、違反対応、作品申請の処理。管理者権限は原則付けない |
| 作品主 | 作品の方針と採否を決めるための表示用ロール。サーバー全体の管理権限は付けない |
| 参加者 | 許可されたフォーラムへの投稿・返信、通常の交流と VC |
| 新規参加者 | ルール閲覧と自己紹介など最小範囲。運営が確認後、参加者へ |

作品主というロールだけで「自分の作品だけを自由に管理」できるわけではないため、投稿整理や権限変更は運営に依頼する。作品別の閲覧制限が必要な場合は、作品別ロールとチャンネル権限を追加する。Discord の権限はサーバー、カテゴリ、チャンネルで設定できる。[Discord: Setting Up Permissions FAQ](https://support.discord.com/hc/en-us/articles/206029707-Setting-Up-Permissions-FAQ)

ルールには次を明記する。

- 批評は作品主が求めた範囲と強さに合わせる。人格攻撃、嘲笑、執拗な指摘はしない。
- ファンアート・二次創作は作品ごとの許諾に従い、原作と作者を明記する。公開、改変、収益化、AI 利用の可否は作品主が別途指定する。未指定なら個別に確認する。
- 他人の原稿・設定・会話をサーバー外へ転載しない。ネタバレとセンシティブな内容は投稿タイトルやタグで予告する。
- モデレーターに相談する窓口を設け、警告、タイムアウト、退出措置の判断者を決める。

招待は少人数へ個別発行し、AutoMod のスパム・大量メンション検出と運営通知を設定する。日本語の攻撃表現の検出を自動化する場合はカスタム語句を使う。ただし文脈判断が要るため、人による対応を残す。Discord の既成の語句リストとスパム検出は英語向けと説明されている。[Discord: AutoMod FAQ](https://support.discord.com/hc/en-us/articles/4421269296535-AutoMod-FAQ)

## 4. 作業 VC

まず `作業室` を1つ設置する。参加者ロールに「接続」「発言」「Video」を与えると画面共有できる。無言作業でもよく、入退室時に挨拶を強制しない。相談したいときは VC のテキストチャットか `#創作相談` に目的を書く。画面共有前には私的な通知や非公開原稿が映らないか確認する。攻撃的な発言への対処は招待制、通報先、モデレーター対応で行う。画面共有は Discord の `Video` 権限で制御される。[Discord: Go Live and Screen Share](https://support.discord.com/hc/en-us/articles/360040816151-Go-Live-and-Screen-Share)

## 5. このリポジトリとの接続

現在のリポジトリは `KUWAOTA/novels` の GitHub リモートを持つ。まずは作品フォーラムに**共有を許可したファイル・公開ページへのリンク**を手動で置く。Discord は議論の場、リポジトリは本文と設定の管理場所とする。非公開の下書き、個人情報、未公開の展開を含むファイルを一括同期しない。

次の段階で、共有対象を決めたうえで `#公開更新` に GitHub の push 等を通知できる。Discord の Webhook URL の末尾に `/github` を付け、GitHub のリポジトリ設定で Webhook を登録する方法が公式に案内されている。ただしこの方式は選択したイベントの更新情報が流れるため、作品本文の公開可否とコミット名・ファイル名の露出を確認してから使う。Webhook URL は秘密として扱う。[Discord: Intro to Webhooks](https://support.discord.com/hc/en-us/articles/228383668-Intro-to-Webhooks) / [GitHub: Creating webhooks](https://docs.github.com/en/webhooks/using-webhooks/creating-webhooks)

Discord 上の採用済みアイデアをリポジトリへ自動書き戻す機能は初期構成に含めない。作品主が採否を決めて要約を反映する運用から始め、件数が増えた場合に限定権限の Bot や仲介処理を設計する。

## 6. Bot の導入順

1. **初期: Bot なし。** フォーラム、ロール、VC、AutoMod だけで運用を始める。
2. **作品申請が増えたら:** 申請フォームまたは限定権限の Bot で申請を整理。チャンネル作成は当面モデレーターが行う。
3. **更新通知が必要になったら:** GitHub Webhook を公開更新専用チャンネルへ接続。
4. **実需が出たら:** 投票、作業時間記録、作品索引などの Bot を個別に検討する。導入前に必要権限、投稿内容の取得範囲、運用者、停止時の代替手順を確認する。

## 7. 実装前の確認事項

- 最初の参加者と管理担当者は誰か。招待制のまま始めるか。
- 初期登録する作品名と作品主は何か。各作品の閲覧範囲は全員向けか。
- 作品ごとの批評、ファンアート、二次創作、外部公開、AI 利用の許諾はどうするか。
- `KUWAOTA/novels` から Discord に共有してよい範囲はどこまでか。
- 既存 Discord サーバーを操作できる接続手段があるか。

## 初期設定の順序

1. 既存サーバーの所有者、権限、公開範囲を確認する。
2. コミュニティ機能と安全設定を有効化する。
3. ロールと基本チャンネルを作成し、権限を参加者視点で確認する。
4. 最初の作品フォーラムを作り、投稿ガイドと見本投稿を置く。
5. VC の接続と画面共有を実際に試す。
6. 少人数を招待して、作品申請・投稿・通報の流れを試す。
7. 必要に応じて Webhook や Bot を追加する。
